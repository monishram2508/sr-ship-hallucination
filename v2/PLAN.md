# v2 plan: retrain a ship-only detector with super-resolved images

v1 ran an off-the-shelf 15-class DOTA detector on bicubic and Real-ESRGAN restorations of 4x-degraded
tiles. A reviewer pointed out that the detector had never seen SR imagery, so v1 mixes two effects:
SR inventing detail, and a detector meeting SR artefacts for the first time. v2 separates them by
training small ship-only detectors with and without restored images in the training data.

**Q1.** Does including SR images in training reduce false ships and improve recall on SR inputs?
**Q2.** With each detector trained on the kind of image it is tested on, does the SR pipeline still
invent more vessels than the bicubic pipeline?

Either answer is a result. If retraining on SR removes most of the invention, the write-up says so.

## 1. Ground rules this plan keeps

- v1 files and results are never modified. v2 imports v1 code read-only: `scripts/common.py` by import,
  and `scripts/03_degrade_sr.py` (whose `degrade()` and `run_sr()` are the exact v1 functions) by
  `importlib`, so v2 cannot drift from v1's degradation or SR path.
- All new work lives in `v2/`, on the local branch `v2-retrain`. Nothing is pushed.
- Committed files hold no absolute paths, usernames or company names. DOTA-derived imagery,
  weights and training runs are gitignored (`v2/.gitignore`).
- Every number in the write-up is read from a file in `v2/results/` that code wrote.

## 4. Upload size and GPU hours

**Upload.** One private Kaggle dataset: the 900 HR training tiles exactly as the v1 tiling code
writes them (JPEG crops from ultralytics' `crop_and_save`, about 220 KB each by the v1 tile
average, so about 0.2 GB), their single-class labels, the manifest with per-tile LR hashes, five
local SR outputs for a cross-device check, and the v2 code. No test-set imagery is uploaded. DOTA
is academic-use only, so the dataset must stay **private**. Exact size is printed by
`03_package_for_kaggle.py`.

**GPU.** Per run: about 810 training images (HR) or 1,620 (HR + restored), batch 8, so about
10,100 forward/backward passes for every condition. Estimate 0.2–0.35 s per batch on a T4 at
1024 px with AMP, plus per-epoch validation, giving **about 40–70 minutes per run and 6–11
GPU-hours for all 9**, inside Kaggle's 30-hour weekly quota. The notebook's timing cell replaces
this estimate with a measured epoch time before anything long is launched. Bicubic + SR for 900
tiles on the GPU adds about 10 minutes once.

## 5. Phases in detail

### Phase 0: audit the v1 SR pipeline

Checks: channel order in and out, dtype/range/clamp/rounding, fp32 vs fp16, eval mode and
`no_grad`, greyscale tiles, tiling seams, Gaussian kernel size, the same LR feeding both arms,
lossless formats. Reference: the official `realesrgan` package (RealESRGANer, fp32, CPU, tile 0)
on 5 Set B LR tiles, compared to v1's SR PNGs by PSNR, at both `pre_pad=0` (the official
script's default) and `pre_pad=10` (the class default). Device effect is separated from
implementation effect by also running v1's spandrel path on CPU. Visual grid of 8 tiles including
P1751. Report: `v2/results/phase0_sr_audit.md`.

Already found while planning (details in the Phase 0 report):

- 67 of 150 Set B tiles and 25 of 100 Set A tiles are greyscale (three identical channels).
  Real-ESRGAN writes colour into them; HR, LR and bicubic stay exactly grey. This is what the
  official package also does for a 3-channel file (it only converts back to grey for 1-channel
  input), so it is not an implementation bug, but it is a defensible alternative pipeline.
  **v1b** re-runs the v1 detector on SR outputs converted back to grey on grey tiles and reports
  v1 vs v1b side by side.
- SR's v1 firing is concentrated on colour tiles, not grey ones (38/83 vs 5/67 at conf 0.25),
  so false colour is unlikely to be what drives v1's result. v1b measures it rather than assuming.

### Phase 1: ship-only training set from DOTA train

- Windows from ultralytics' own `get_windows` / `get_window_obj` (1024 px, gap 200, IoF 0.7),
  the same code path v1's tiling used; only selected windows are cropped, via `crop_and_save`.
  Exactly-1024 windows only, as in v1.
- Positives: at least one ship assigned to the window.
- Negatives: **no ship polygon touching the window at all** (IoF > 0), not just "no ship assigned".
  With IoF 0.7, a window can visibly contain a cut-off ship and still carry no ship label; such a
  window would teach the model that a ship is background.
- Hard negatives: no ship and at least one harbor, small-vehicle or large-vehicle label. Random
  negatives: drawn from the remaining no-ship windows.
- Sampling seed 0: 600 positives, 150 hard negatives, 150 random negatives.
- 90/10 split by source image, greedy over a seeded shuffle of source images until the validation
  side holds 10% of tiles.
- Labels: ship -> class 0, everything else dropped. **Coordinates are clipped to [0, 1].**
  Ultralytics rejects the *whole image* if any label point is outside [-0.01, 1.01], and IoF-0.7
  assignment leaves edge ships up to 30% outside the window, so without clipping some positives
  would silently vanish from training. The number of clipped polygons is logged.
- `v2/data/trainset_manifest.csv`: tile id, source image, window x0/y0, split, pos/neg,
  hard-negative flag, ship count, clipped-polygon count, HR and LR hashes.

### Phase 2: degrade and restore the training tiles

Local: v1's `degrade()` on every training tile -> LR, plus a hash of each LR array, plus SR of 5
tiles on MPS for the cross-device check. Kaggle: re-degrade from the uploaded HR tiles, assert the
hashes match (cross-platform determinism of OpenCV blur + area resize), then bicubic and v1's
`run_sr()` on the GPU in fp32. PSNR between Kaggle SR and local SR on the 5 check tiles is
reported; it should be well above 40 dB.

### Phase 3: training

`YOLO("yolov8n-obb.yaml").load("yolov8n.pt")`: COCO weights wherever shapes match, never the DOTA
OBB weights. `imgsz=1024, single_cls=True, batch=8, flipud=0.5, deterministic=True, patience=0,
optimizer=auto, cache=disk`, everything else default. The resolved optimizer is logged; with
equal iteration counts `auto` resolves identically for all conditions (AdamW, lr0 0.002).

| Condition | Train images | Epochs | warmup_epochs | close_mosaic |
|---|---|---|---|---|
| M_HR | HR | 100 | 3.0 | 10 |
| M_SR | HR + SR | 50 | 1.5 | 5 |
| M_BIC | HR + bicubic | 50 | 1.5 | 5 |

Seeds 0, 1, 2. Seed 0 for all three conditions first. `last.pt` is evaluated. Each run saves
`last.pt`, `results.csv`, `args.yaml`, the data YAML and manifest it used, the resolved
optimizer, and the batch size actually used (ultralytics can auto-reduce on OOM; that is logged).

### Phase 4: predictions

All 9 models plus the v1 detector, on HR, bicubic and SR versions of Sets A and B, at
`conf=0.01, max_det=1000`. One CSV: model, condition, seed, set, version, tile, conf, eight corner
coordinates in pixels. Thresholds are applied afterwards.

**Regression gate:** v1's detector predictions, thresholded at 0.25 and 0.5 afterwards, must
reproduce v1's `setA_fixed_threshold.json` (TP/FP/FN) and `setB_counts.csv` (per tile) exactly.
If they don't, the v2 evaluation code is wrong and nothing downstream is trusted.

### Phase 5: evaluation

- Set A: greedy, highest-confidence-first matching with ultralytics' `batch_probiou`, IoU 0.5, at
  0.25 and 0.5: P, R, F1, TP, FP, FN. AP50 from the same matching over all detections >= 0.01,
  101-point interpolation via ultralytics' `compute_ap`.
- Set B firing: share of tiles with at least one detection, at 0.25 and 0.5, for every model and
  version including HR. Set B was verified empty with the **v1** detector only, so a v2 model can
  fire on HR. Two numbers are therefore kept: raw firing, and firing beyond the original (fired on
  this version and not on HR, same model, same threshold).

### Phase 6: audit

Pool every Set B detection >= 0.25 across models, seeds and versions (HR included). Cluster per
tile, highest confidence first, joining a cluster when probIoU with its seed box >= 0.5. A cluster
whose seed box has probIoU >= 0.5 with a v1-audited box inherits that box's final verdict. v1's
audit key stores crop windows, not polygons; the polygons are recovered from the v1 detector's
Phase 4 predictions and checked against the key's crop windows and confidences exactly.
Unmatched clusters become new blind crops from the original tile, rendered with v1's crop code,
shuffled with seed 0 before ids are assigned. 25 v1 crops (stratified by pass-1 verdict, seed 0)
are mixed in as hidden repeats for Cohen's kappa.

**Checkpoint 4 stops here with the crop count.**

### Phase 7: statistics (pre-registered before any v2 result exists)

- **C1 (the reviewer's):** SR test images, M_SR vs M_HR, paired by seed.
- **C2 (fair pipelines, the new headline):** M_SR on SR vs M_BIC on bicubic, paired by seed.
- **C3 (references):** M_HR on HR (ceiling) and the v1 detector rows.
- Metrics: Set B firing (raw and beyond-original) and invention (lower and upper bands, with and
  without P1751); Set A P, R, F1 at 0.25 and 0.5, and AP50.
- **Primary endpoints:** Set B invention, upper and lower bands, conf 0.25, all tiles; Set A
  recall at conf 0.25. Everything else is secondary and reported descriptively.
- Every number per seed, then mean ± SD over seeds. Tile-level tests per seed: exact McNemar on
  tile outcomes for Set B; paired bootstrap over tiles (10,000 resamples, seed 0) for every
  difference, including Set A recall as a ratio of sums. Secondary: tile bootstrap of the
  seed-averaged difference.
- For every comparison: does the effect have the same sign in all 3 seeds?
- Kappa: repeats vs v1 pass-1 verdicts (same rendering), and vs final verdicts.

### Phase 8: write-up

`v2/results/summary.md` and `v2/README.md`, as in the brief. Checkpoint 5 before committing.

## 7. What in the brief I think is wrong or risky

1. **Label bounds would silently shrink the training set.** See Phase 1: clip, and log how many.
2. **"Equal training budget" needs more than halving epochs.** Warmup and `close_mosaic` are in
   epochs, so they are halved for the 2x-data conditions. The optimizer is left on `auto`, which
   resolves the same way for all conditions because the iteration counts match; pinning AdamW by
   hand would *not* be equivalent, because `auto` also zeroes `warmup_bias_lr`.
3. **Set B is "empty" only for the v1 detector.** New models can fire on HR Set B tiles, so raw
   firing is no longer invention-free on the original. Beyond-original firing and the audit
   handle it.
4. **Equal steps means unequal HR exposure.** M_SR and M_BIC see each HR tile half as often as
   M_HR. That is inherent in the design; it may cost them a little on HR, and C3 will show it.
5. **"Random no-ship tiles" can contain cut-off ships.** Hence the stricter IoF > 0 rule.
6. **`deterministic=True` is best-effort on GPU.** With AMP and cuDNN, runs are not bit-exact;
   seeds still fix initialisation and data order. That is exactly why 3 seeds are needed.
7. **A nano model on ~540 training positives will be much weaker than v1's 15-class small
   model.** Absolute recall will drop; the comparisons are within v2.
8. **DOTA labels are incomplete,** so some negatives may hold unlabelled vessels. That affects
   all three conditions equally and goes in the limitations.
9. **Overlapping tiles.** With a 200 px gap, neighbouring training tiles share pixels. The
   by-image split keeps validation clean; within training they act as mild augmentation.
10. **COCO pretraining includes a "boat" class.** That is a generic prior, not DOTA leakage, and
    it is the same for every condition.
11. **Real-ESRGAN was trained on a synthetic degradation family that includes Gaussian blur, but
    with noise and JPEG too.** Our blur + area model is a subset of that family, not a mismatch
    bug, but v2 still tests one blind SR model with no satellite fine-tuning.
